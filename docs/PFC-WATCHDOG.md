# PFC watchdog

实现位于现有 switchd 的唯一 SDK 执行线程，默认关闭。Web 草稿中的 `qos.roce.watchdog` 经配置编译、YANG、L2 计划、硬件事务回读和回滚下发到参与端口；低频 Python 诊断模块不执行恢复写入。

## 策略

| 参数 | 默认值 | 范围 |
|---|---:|---:|
| enabled | false | 只对已启用 RoCE 的参与端口生效 |
| detect_ms | 5000 | 1000–60000 |
| recovery_ms | 100 | 100–1000 |
| cooldown_ms | 30000 | 10000–600000，且不小于检测时间 |

每100毫秒在 owner 内检查。只有链路 Up、TC3 对应 pause class3、实际 RX PFC 掩码为8、TC3 非空、剩余暂停 quanta 非零，而且连续收到新的 PFC、普通 Pause 计数不增长、端口普通数据发送计数不增长，才累计停滞时间。采样间隔超过300毫秒、读取失败、链路/物理端口变化或维护都会重新开始检测。

FM10000 缺少可用的逐 TC 发送计数，因此采用端口 unicast/multicast/broadcast TX 帧计数。其他队列继续发送时会否决恢复，可能漏检 TC3 停滞。100毫秒采样也无法证明两个采样点之间从未恢复；这是一种保守的停滞检测，不是所有 PFC 死锁的完备判定。

## 恢复与事务边界

动作通过受支持的 `FM_PORT_RX_CLASS_PAUSE` 临时解除 priority3 的暂停响应。先保存 RX 掩码和唯一物理端口，再记录恢复责任，最后尝试 SDK 写入。`CM_PAUSE_CFG` 使用 uncached 读，不能仅用 SDK 缓存判断写入成功。

恢复窗口结束后，同时核实 SDK 缓存和实际硬件掩码。写入失败、部分写入、读回不一致都保留恢复责任；不会通过关闭 watchdog 或换配置丢弃未恢复状态。端口映射意外变化时，不把保存的掩码写到另一个物理端口。

开始配置或回滚前先恢复全部临时覆盖，失败则拒绝继续，不允许将临时 mask0 捕获为配置原值。端口维护、counter reset、眼图控制和 owner 正常退出前也执行恢复。配置事务或不可用的控制状态暂停新的检测。

所有 SDK 操作仍串行执行。恢复窗口是调度目标，SDK 调用阻塞或进程被强制终止时不能保证按时恢复；未恢复状态会阻止正常配置继续。服务重新启动时依赖现有闭端口初始化及配置回放恢复稳定策略。

不写 `CM_EGRESS_PAUSE_COUNT`：硬件 sweeper 启动后禁止软件修改该计数器。恢复可能导致丢包，必须结合实际网络验证。界面分别显示检测次数、掩码恢复次数、失败和采样间断；掩码恢复不能直接称为业务恢复或无损。

## 验收方法

在隔离网络中分别记录 watchdog 关闭与开启时的持续暂停、队列释放和掩码恢复。检查端点真实接收进度、PFC 报文、配置终态、错误及重传；只看计数器增量不能证明无损。恢复参数、默认 QP 超时和长期负载必须按实际端点验证。方法见 [硬件验收](HARDWARE_ACCEPTANCE.md)。
